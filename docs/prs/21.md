# End runs whose request gets no response or an unreadable one

Closes #21. Follows the plan's frontend work ([docs/plans/dyalog-runner.md](../plans/dyalog-runner.md), Frontend), after use of the local instance.

## Summary

The frontend ends every run it starts, whatever the server does. A run request that gets no response is given up once the server's time limit and a margin of 10 s have passed. The limit comes from `/api/v1/version`, which now reports it as `timeoutMs`. Each kind of failure has its own message: no response in time, a 200 response that is not a run result, an error status, and a connection failure. An error status whose body is not plain text shows a fixed description instead of the body. After a failed run, Output and Debug are empty, so a previous run's results are not taken for this run's.

## How it was tested

Go unit and integration tests for `timeoutMs`. Playwright tests in CI against the container, as for #7, with the run and version requests answered by the test where a failure is needed. A local preview server (`api.NewHandler` serving `web/`, with an executor running the dev container's `dyalogscript`) gives earlier feedback for the tests that need no container.

**Decisions in the tests**

- No response:
  - The test holds the run request unanswered and answers the version request with the server's own response, with `timeoutMs` set to 2000. A deadline that ignored the reported limit would fall at the default (10 s plus the margin) and miss the test's window.
  - 7 s after the run starts (the limit plus half the margin), the Run button must still be running. By 15 s, a message titled "Error" must say the server did not respond, and the button's image must equal the one before the run.
- Unreadable responses: a 200 with an HTML page, with JSON cut off mid-field, and with JSON that has none of the result's fields. Each must show an "Error" message containing "response could not be read" and leave the button at rest.
- Error statuses:
  - A 502 with an empty body, and one with an HTML page, must show "Error 502" over the text "The server could not run the program."
  - A 429 with a plain-text reason must show "Error 429" over the reason, without its trailing newline.
  - The empty-body test also covers HTTP/2, which has no status text: the description must not come from the status text.
- Results:
  - A real run fills Output with `4` and Debug with a `DOMAIN ERROR`. A second run then gets an unreadable response, a 429, or a reset connection, and Output and Debug must then be empty.
  - A run the user cancels must leave both as they were.
- Messages are found by their visible title, so the hidden "Command mode" message plays no part.
- A response whose body stalls after its headers is not tested: the test's request interception can only answer whole bodies. The deadline covers it the same way, since it aborts the body's reading as well as the request.

**Expected failures**

- `TestGetVersionReportsTheRunTimeLimitInMilliseconds`: `timeoutMs` is absent.
- `TestVersionReportsTheWallClockLimitSetBySandboxTimeout`: `timeoutMs` is absent.
- No response: the button is still running at 15 s, and no message appears.

**Anticipated implementation**

1. `internal/api/server.go`: `/api/v1/version` adds `timeoutMs` from `Options.Timeout`. `cmd/runner-api/main.go` passes the configured limit.
2. `web/frontend.js`:
   - The page reads `timeoutMs` with the version, and assumes 10 s until then or if the request fails.
   - Each run arms a timer for the limit plus 10 s. If the limit arrives after the run starts, the timer extends to the new deadline when it fires. When it expires, the run is aborted and reported as having had no response, unlike a cancellation by the user.
   - A 200 response is a run result only if it parses as JSON with string `stdout` and `stderr` and numeric times; anything else is reported as unreadable.
   - An error status shows its body only when the response is `text/plain` and the body is not empty, and the fixed description otherwise.
   - Every failure empties Output and Debug.
3. `README.md`: the description of `/api/v1/version` lists `timeoutMs`.
