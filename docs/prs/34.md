# Deploy the public instance without --privileged

Closes #34. Part of #1. Follows #33.

## Summary

The public instance runs the sandbox container as #33 established: with `CAP_SYS_ADMIN` added, AppArmor and Docker's masked paths unconfined, and the seccomp profile `deploy/seccomp.json`, instead of `privileged: true`. `deploy/setup-host` installs the profile beside the compose file.

## How it was tested

Deployment tests in CI, on a runner that `deploy/setup-host` provisions as the public instance, as for #9.

**Decisions in the tests**

- The container's configuration comes from `docker inspect`: `HostConfig.Privileged`, `CapAdd` and `SecurityOpt`. Docker keeps a seccomp profile there as `seccomp=` followed by the profile's JSON, which the test compares, parsed, with `deploy/seccomp.json`.
- The capability may be written with or without its `CAP_` prefix; both name the same capability.
- The new tests run before the update test, which replaces the running image.

**Expected failures**

- `TestSandboxContainerIsNotPrivilegedAndAddsOnlySysAdmin`: the container is privileged and adds no capability.
- `TestSandboxContainerUnconfinesAppArmorAndMaskedPathsAndUsesTheSeccompProfile`: the container has no security options.
- `TestSetupHostInstallsTheSeccompProfile`: `/opt/sandbox/seccomp.json` does not exist.

**Evidence**

- CI run [45576499155](https://github.com/abrudz/sandbox/actions/runs/45576499155) on `722404d`: lint, the unit tests and the image job pass; of the deployment tests, the other nine pass and exactly the three new ones fail:
  - the container is privileged and adds no capability (`[]`);
  - its only security option is `label=disable`, so `apparmor=unconfined`, `systempaths=unconfined` and the seccomp profile are missing;
  - `/opt/sandbox/seccomp.json` does not exist.

**Anticipated implementation**

- `deploy/compose.yaml`: the sandbox service loses `privileged: true` and gains `cap_add: [SYS_ADMIN]` and `security_opt` with `apparmor=unconfined`, `systempaths=unconfined` and `seccomp=/opt/sandbox/seccomp.json`.
- `deploy/setup-host` installs `deploy/seccomp.json` as `/opt/sandbox/seccomp.json`, mode 644, and recreates the sandbox container when the profile changes, since Docker reads it only when creating the container.
- The plan's public instance entry and the README's public instance section say how the container runs.

### Cycle 2: GREEN

**Changes**

- `deploy/compose.yaml`: the sandbox service has no `privileged`. It has `cap_add: [SYS_ADMIN]` and `security_opt` with `apparmor=unconfined`, `systempaths=unconfined` and `seccomp=./seccomp.json`, which Compose resolves against `/opt/sandbox` and reads when it creates the container.
- `deploy/setup-host` installs `deploy/seccomp.json` as `/opt/sandbox/seccomp.json`, mode 644. When the profile changes and the sandbox container predates the run, it recreates that container with `up -d --force-recreate sandbox`: Compose compares the option's text, not the file's contents, and Docker reads the profile only when it creates a container. A container that `up -d` has just created already has the new profile.
- `README.md`: the public instance's container runs with the four options from Running it locally, and `setup-host` installs the profile. The plan's public instance entry names the flags.

**Test changes in this cycle**

- `TestSandboxContainerUnconfinesAppArmorAndMaskedPathsAndUsesTheSeccompProfile` looked for `systempaths=unconfined` among the security options. The Docker CLI and Compose both turn that option into empty `MaskedPaths` and `ReadonlyPaths` and drop it from `SecurityOpt` (`parseSystemPaths` in docker/cli, `parseSecurityOpts` in docker/compose). The test now requires both lists to be present and empty.

**Evidence**

- Locally: `gofmt`, `go vet -tags deploy` and `bash -n deploy/setup-host` pass.
