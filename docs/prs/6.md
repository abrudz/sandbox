# Harden the HTTP API against malformed and excessive requests

Closes #6. Work item 5 of [docs/plans/dyalog-runner.md](../plans/dyalog-runner.md).

## Summary

`POST /api/v1/run` refuses malformed requests (400), requests whose code and input exceed the request limit or whose body is far larger than any valid request (413), and more than 16 arguments or an argument over 1 KiB (400). It answers 429 at once when every concurrency slot is busy, or when the client already has its maximum number of runs in progress or has started its maximum number of runs in the last minute. Clients are told apart by their address, or by `X-Forwarded-For` when the request comes from a trusted proxy. On SIGTERM, runs in progress finish, every new request gets 503, and `runner-api` exits once the last run has answered. The limits come from `SANDBOX_REQUEST_LIMIT`, `SANDBOX_CONCURRENCY`, `SANDBOX_CLIENT_CONCURRENCY`, `SANDBOX_CLIENT_RATE` and `SANDBOX_TRUSTED_PROXIES`, with the plan's defaults: 64 KiB, the number of CPUs, 2, 30 per minute and no trusted proxies.

## How it was tested

Unit tests run in the dev container with `go test ./...`; they drive the handler with fake executors, one of which holds runs until released, and with a fake clock for the per-minute limit. Integration tests run in CI against the CI container and containers started with their own settings (plan, Development environment); each cycle below links its CI run.

**Decisions in the tests**

- The request limit applies to the decoded code plus input, so a request of exactly the limit passes and one byte more gets 413. A body far larger than any valid request also gets 413 without being decoded: the test pads a small request with 1 MB of whitespace.
- The argument limits (16 arguments, 1 KiB each) are fixed by the API contract rather than configurable.
- "Immediately" means under 500 ms in the slot test. Every unit-test request is abandoned after 3 s, so a refusal that never comes fails the test instead of hanging it; an abandoned request reports 200, the recorder's default.
- Clients are identified by their address. Behind a trusted proxy, the client is the right-most `X-Forwarded-For` entry. The proxy appends the address it saw, so entries to its left are the client's own claims, and a forged entry does not create a new client. `X-Forwarded-For` from any other peer is ignored.
- The per-minute limit counts runs that start; refused requests do not count.
- While draining, every new request gets 503, including `/healthz`, so a proxy stops sending traffic.
- The SIGTERM test sends the signal with `docker kill --signal TERM` to a container of its own. tini forwards it to `runner-api`. The test requires a 503 for a new run within a second, the run in progress to answer 200 with its output, and the container to exit with status 0 within 15 s.

**Expected failures**

- The new config unit tests: the new limits read as zero (or empty) and invalid values are accepted.
- Every new handler test except `TestPostRunAnswers400ForMalformedJSON`, which already passes from #3: requests that should get 400, 413 or 429 get 200, and during `Drain` new runs are still accepted. The three tests that hold runs open wait 3 s for a refusal that never comes.
- `TestTheServiceAnswers400ForMalformedJSONAnd413ForAnOversizedRequest`: 70 KiB of code gets 200.
- `TestSandboxConcurrencySetsTheNumberOfSlots` and `TestSandboxClientRateSetsThePerMinuteLimit`: the second run with one slot, and the third run in a minute with a rate of 2, get 200.
- `TestSIGTERMLetsRunsFinishRefusesNewOnesAndEndsTheService`: `runner-api` exits at once on SIGTERM, so the next request is reset (`connection reset by peer`).

**Evidence**

CI run [44505244963](https://github.com/abrudz/sandbox/actions/runs/44505244963) on `4d885a2`: lint passes, the image builds; both jobs fail at their test steps with exactly the failures listed above, and all 38 integration tests from #2 to #5 pass. The unit tests fail the same way locally with `go test ./...`.

**Anticipated implementation order**

1. `config.FromEnv`: the five new variables, with validation; `TrustedProxies` stays nil when unset, and a bare address becomes a /32 or /128 prefix.
2. `internal/api`: a drain middleware; request decoding with `http.MaxBytesReader` (413), the argument checks (400) and the code-plus-input check (413); then client identification, the per-minute window, the per-client count and the global slots, refusing at once with 429 and releasing on return. A limit of zero means no limit, which keeps the unit tests from #3 unchanged.
3. `cmd/runner-api`: passes the limits, and on SIGTERM or SIGINT drains the server (bounded by the run timeout plus a margin), shuts the HTTP server down and exits 0.
