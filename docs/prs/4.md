# Enforce run limits and clean up after every run

Closes #4. Work item 3 of [docs/plans/dyalog-runner.md](../plans/dyalog-runner.md).

## Summary

Every run is limited to a wall-clock time and keeps at most a fixed number of bytes from each of stdout and stderr; both limits come from the environment (`SANDBOX_TIMEOUT`, `SANDBOX_OUTPUT_LIMIT`) with the plan's defaults of 10 s and 128 KiB. A run past its time limit is killed and reported as `timedOut`; output past the cap is dropped and flagged while the program runs on. A client that disconnects ends its run within a second, and no run leaves processes, cgroups or its per-run directory behind.

## How it was tested

Unit tests for reading the limits run in the dev container with `go test ./...`. Integration tests run in CI against the CI container and against containers they start with their own environment (plan, Development environment); each cycle below links its CI run.

- `startContainer` starts another container from the image under test with extra environment variables, waits for `/healthz`, and removes it when the test ends (printing its log if the test failed).
- `leftovers` lists, through `docker exec`, what runs left in a container: processes other than the container's PID 1, `runner-api` and the listing script itself (each with its state, so a zombie shows as `Z`), entries under `/tmp/sandbox-jobs`, and cgroups other than the entry point's leaf `init`.

The tests that inspect leftovers start a container of their own. The first RED run used the shared CI container, and a process left by the cancellation test also failed the completed-run test that followed it.

`run` and `request` gain `runAt` and `requestAt` variants that take the container's URL.

**Decisions in the tests**

- Programs wait with `⎕DL`, so the tests depend on wall-clock time only, not on CPU speed.
- The stderr test writes through `⎕SH'yes x | head -c 200000 >&2'`: APL itself writes only error messages to stderr, and a shell command's stderr reaches the interpreter's.
- The cancellation test waits until the `dyalog` process is visible before disconnecting, then requires `leftovers` to be empty within one second of the disconnect.
- Per-run cgroups do not exist until the memory, CPU and process limits arrive with #5; the cgroup part of the leftover check guards that work.

**Expected failures**

- The four config unit tests: "not implemented".
- `TestRunPastTheWallClockLimitIsKilled`: `timedOut` is false; nsjail's backstop `time_limit` of 10 s kills the run at about 10 s without the API knowing why.
- `TestStdoutPastTheCapIsTruncatedAndFlagged` and `TestStderrPastTheCapIsTruncatedAndFlagged`: all output comes back (200043 and 200000 bytes) and nothing is flagged.
- `TestClosingTheConnectionKillsTheRunWithinOneSecond`: the cancelled run leaves a zombie `dyalogscript`. Go's default cancellation sends SIGKILL to nsjail, so nsjail never reaps the jailed process; its parent-death signal kills it, the kernel re-parents it to `runner-api`, which is PID 1 and does not reap it.
- `TestNothingRemainsAfterATimedOutRun` and `TestSandboxTimeoutSetsTheWallClockLimit`: the container ignores `SANDBOX_TIMEOUT=2s`, so the run is not timed out.
- `TestNothingRemainsAfterACompletedRun` passes: a run that ends by itself already leaves nothing. The test guards that.

**Evidence**

CI run [44481545517](https://github.com/abrudz/sandbox/actions/runs/44481545517) on `1c6b743`: lint passes, the image builds; both jobs fail at their test steps with exactly the failures listed above, and every test from #2 and #3 passes. The cancellation test reports `["process 15 state Z dyalogscript"]` one second after the disconnect. The config unit tests fail the same way locally with `go test ./...`.

The first RED run, [44480774810](https://github.com/abrudz/sandbox/actions/runs/44480774810), used the shared CI container for the leftover tests and showed the cross-test failure that led to the separate containers.

**Anticipated implementation order**

1. `internal/config.FromEnv`: `SANDBOX_TIMEOUT` as a positive Go duration and `SANDBOX_OUTPUT_LIMIT` as a positive byte count, defaults 10 s and 131072, errors naming the variable. `runner-api` refuses to start on an invalid value.
2. Output caps: stdout and stderr go through a writer that keeps the first `OutputLimit` bytes, records truncation, and keeps draining so the program never blocks on a full pipe.
3. Wall-clock limit in the executor: a timer at `Timeout` marks the run as timed out and stops it. nsjail's own `time_limit` counts whole seconds, so it stays as a backstop a second or more after the configured limit.
4. Stopping a run (timeout or client disconnect): SIGTERM to nsjail, which kills the jail with SIGKILL, reaps it, removes its cgroup and exits; if nsjail has not exited a second later, SIGKILL, and the jail dies with it through its parent-death signal. The per-run directory is removed once nsjail has exited.
5. `tini` as the container's PID 1, so a process orphaned by that last-resort SIGKILL is reaped rather than left as a zombie under `runner-api`.
