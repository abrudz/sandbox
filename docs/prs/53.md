# Drop the sandbox container's unneeded capabilities

Closes #53. Part of #1.

## Summary

The sandbox container drops every capability and adds back only `CAP_SYS_ADMIN`, `CAP_SETUID` and `CAP_SETGID`: the entry point remounts the cgroup filesystem and Docker's seccomp profile allows nsjail's namespace, mount and `pivot_root` calls only with `CAP_SYS_ADMIN`, and nsjail maps the jail's uid and gid, which are not its own, with the other two. The jail's own capabilities come from its new user namespace, not from the container. The compose file, the README's `docker run` command, CI's container and the integration tests' containers use the same set.

## How it was tested

An integration test reads the CI container's effective and bounding capability sets, and a deployment test reads the compose-started container's capability settings and sets, on a runner `setup-host` has provisioned. Every other suite runs in containers with the reduced set.

**Decisions in the tests**

- Both tests read `CapEff` and `CapBnd` of the container's PID 1, tini, which runs as root like runner-api and nsjail, and require each to be exactly bits 6, 7 and 21: `SETGID`, `SETUID` and `SYS_ADMIN`. The bounding set limits every process in the container; the effective set is what root there can use.
- The deployment test also requires `HostConfig` to drop `ALL` and add exactly those three, with or without the `CAP_` prefix, which Docker accepts both ways.
- The rest of the suites are the evidence that the set suffices: every run, limit and isolation test runs in a container started with it. If they show that another capability is needed, it joins the set in both tests, with its reason.

**Expected failures**

- `TestContainerHoldsOnlySysAdminSetuidAndSetgid`: the CI container holds Docker's 14 default capabilities and `SYS_ADMIN`.
- `TestSandboxContainerIsNotPrivilegedAndHoldsOnlySysAdminSetuidAndSetgid`: the compose-started container drops nothing, adds `SYS_ADMIN` alone, and holds the same 15 capabilities.

**Evidence**

- Locally: `gofmt` and `go vet` (with `-tags integration` and `-tags deploy`) pass. Both tests run in CI only.
- CI run [45797093619](https://github.com/abrudz/sandbox/actions/runs/45797093619) on `ec93c99`: exactly the two tests fail. Both containers' `CapEff` and `CapBnd` are `00000000a82425fb`, Docker's 14 defaults and `SYS_ADMIN`; the compose-started container drops nothing and adds `CAP_SYS_ADMIN` alone. Lint, the unit tests, the other integration and deployment tests and the 52 UI tests pass.

**Anticipated implementation**

- `deploy/compose.yaml`: `cap_drop: [ALL]` and `cap_add` of `SYS_ADMIN`, `SETUID` and `SETGID`.
- `--cap-drop ALL --cap-add SYS_ADMIN --cap-add SETUID --cap-add SETGID` in the README's `docker run`, `.github/workflows/image.yml`, `runFlags` in `test/integration/helpers_test.go` and the plan's two `docker run` commands.
- README and plan: the reason for each capability.

### Cycle 2: GREEN

**Changes**

- `deploy/compose.yaml`: `cap_drop: [ALL]`, and `cap_add` of `SYS_ADMIN`, `SETUID` and `SETGID`.
- `--cap-drop ALL --cap-add SYS_ADMIN --cap-add SETUID --cap-add SETGID` in the README's `docker run`, `.github/workflows/image.yml`, `runFlags` in `test/integration/helpers_test.go` and the plan's two `docker run` commands.
- `image/Containerfile`: `WORKDIR /`. Without `CAP_DAC_OVERRIDE` root cannot enter the base image's working directory, `/home/dyalog`, which the `dyalog` user owns, so runner-api, nsjail and every `docker exec` started in a directory they could not access.
- README: what `SETUID` and `SETGID` are for, and that the container holds no other capability. Plan and `image/entrypoint`: the same.
- No other capability is needed: every run, limit, isolation and deployment test passes with the three.

**Test changes in this cycle**

- `TestImageRunsAJailedProcess` jailed its process with `nsjail --user 99999 --group 99999`, which maps the jailed uid and gid onto root outside the jail ("99999 0 1"). Since Linux 5.12 that mapping needs `CAP_SETFCAP`, and no run makes it: `image/nsjail.cfg` maps 99999 to 99999. The test now jails its process the same way, through a three-line configuration file it mounts into the container, because nsjail's `--uid_mapping` and `--gid_mapping` options need `newuidmap`, which the image does not have.

**Evidence**

- Locally: `gofmt`, `go vet` (with `-tags integration` and `-tags deploy`) and `bash -n image/entrypoint` pass.
- CI run [45797218922](https://github.com/abrudz/sandbox/actions/runs/45797218922) on `03a2e4e`, before `WORKDIR /` and the test change: both capability tests pass, every deployment test passes, and so do the 52 UI tests and every run test. Four integration tests fail. `TestImageRunsAJailedProcess`: nsjail "Couldn't write '10' bytes to file '/proc/7/uid_map' ... Operation not permitted". `TestNothingRemainsAfterACompletedRun`, `TestNothingRemainsAfterATimedOutRun` and `TestClosingTheConnectionKillsTheRunWithinOneSecond`: the `find` they run with `docker exec` reports "Failed to restore initial working directory: /home/dyalog: Permission denied", which the tests read as something left behind.
- CI run [45798385196](https://github.com/abrudz/sandbox/actions/runs/45798385196) on `84674c1`: every job passes. Both containers hold `SYS_ADMIN`, `SETUID` and `SETGID` alone; `TestImageRunsAJailedProcess` jails its process as uid 99999 with those three; the leftover checks find nothing; every other integration test, the 52 UI tests, the unit tests and the deployment tests pass.
