# Run the sandbox container with a read-only root filesystem

Closes #63. Part of #1.

## Summary

The sandbox container runs with a read-only root filesystem and a small tmpfs at `/tmp`, where runner-api keeps each job's directory. Root in the container, where runner-api, nsjail and the entry point run, can no longer change the image's files. Runs are unaffected: they write to the tmpfs mounts nsjail creates for each run, `/tmp` and the working directory, `/home/run`. `deploy/compose.yaml`, the README's `docker run`, CI's container and the integration tests' containers use the same settings.

## How it was tested

An integration test has root in the CI container try to create files in the image's directories and in `/tmp`; a deployment test reads the compose-started container's settings. Another integration test has a run write a file by a relative name and read it back. Every other suite runs in containers with the new settings.

**Decisions in the tests**

- Root in the container holds no `CAP_DAC_OVERRIDE`, but owns `/`, `/etc`, `/usr/local/bin` and `/var`, so only a read-only filesystem stops it there. The test requires the error to say so, so that a permission error does not pass for it.
- `/tmp` must take a file and report the file system type `tmpfs`.
- The deployment test reads `ReadonlyRootfs` and `Tmpfs` from the container's `HostConfig`, as the capability test reads its capabilities.

**Expected failures**

- `TestRootInTheContainerCanWriteOnlyToTmp`: root creates each file, and `/tmp` is on the container's overlay.
- `TestSandboxContainerHasAReadOnlyRootFilesystemAndATmpfsAtTmp`: the compose-started container's root filesystem is writable, with no tmpfs.
- `TestARunWritesAndReadsAFileByARelativeName` passes already.

**Evidence**

- Locally: `gofmt` and `go vet` (with `-tags integration` and `-tags deploy`) pass. The tests run in CI only.
- CI run [45966796841](https://github.com/abrudz/sandbox/actions/runs/45966796841) on `f59b9d2`: exactly the two tests fail. Root in the CI container creates `/marker`, `/etc/marker`, `/usr/local/bin/marker` and `/var/marker`, and `/tmp` is on `overlayfs`; the compose-started container's root filesystem is writable, with no tmpfs mounts. `TestARunWritesAndReadsAFileByARelativeName`, the rest of the suites, lint and the unit tests pass.

### Cycle 2: GREEN

**Changes**

- `deploy/compose.yaml`: `read_only: true` and a tmpfs at `/tmp` of at most 16 MiB, with Docker's default mode, 1777.
- `--read-only --tmpfs /tmp:size=16m` in the README's `docker run`, `.github/workflows/image.yml`, `runFlags` in `test/integration/helpers_test.go` and the plan's two `docker run` commands.
- README: what `--read-only` protects, and what writes to the tmpfs.
- What writes there: runner-api's job directories, each a run's code (at most `SANDBOX_REQUEST_LIMIT`, 64 KiB by default), and nsjail's work directories. nsjail tries `/run/user/0/nsjail/…` first, which the read-only filesystem refuses, and falls back to `/tmp/nsjail.0.…`. 16 MiB holds a job directory for every slot of the largest VM `setup-host` sizes for, with room to spare; runs write to tmpfs mounts of their own, which nsjail sizes.

**Evidence**

- Locally: `gofmt` and `go vet` (with `-tags integration` and `-tags deploy`) pass.
- CI run [45967639346](https://github.com/abrudz/sandbox/actions/runs/45967639346) on `ccb51f8`: every job passes. Root in the CI container gets "Read-only file system" for each file and writes to `/tmp`, a tmpfs; a run writes and reads a file by a relative name; `TestImageRunsAJailedProcess`, with its configuration mounted at `/tmp/jail.cfg` over the tmpfs, jails its process; the compose-started container's root filesystem is read-only with a tmpfs at `/tmp`; the rest of the suites pass.
- `main` was then merged into this branch, after #61, #62 and #64, so that the last run tests the read-only filesystem with runs in cgroups of their own and the jail's own `/etc`. The only conflict was two sets of tests appended to `test/integration/isolation_test.go`; both are kept.
