# Limit the public instance's request size, memory and processes

Closes #39. Part of #1.

## Summary

On the public instance, Caddy refuses a request body larger than runner-api's largest valid body before reading it. The sandbox container has memory and process limits that `deploy/setup-host` derives from the VM: the memory limit leaves 512 MiB for the operating system, Docker and Caddy, and the run concurrency is set so that concurrent runs at their memory and process limits fit within the container's.

## How it was tested

Deployment tests in CI, on a runner that `deploy/setup-host` provisions as the public instance.

**Decisions in the tests**

- runner-api's largest valid body is 6 × (64 KiB + 16 × 1 KiB) + 4 KiB = 495,616 bytes with the default request limit. The refusal test claims one byte more in `Content-Length` and sends nothing. Caddy's `request_body` limit compares `Content-Length` before reading, so it answers 413 at once; runner-api would wait for the body and answer 408 after 15 s. The test therefore tells Caddy's refusal from runner-api's.
- A body of exactly 495,616 bytes, a run padded with whitespace, must still reach runner-api and run. That passes already, and guards against a Caddy limit set below runner-api's.
- The host keeps 512 MiB beyond the container's limit, and the container keeps 128 MiB beyond its runs for runner-api and the bodies it reads. Swap is off: the container's memory plus swap equals its memory.
- The run concurrency, per-run memory and per-run process limit come from the line runner-api logs when it starts, which shows the limits it enforces. The container's process limit must allow every run its 64 processes, plus 64 for runner-api, nsjail and tini.

**Expected failures**

- `TestCaddyRefusesABodyOverRunnerAPIsLimitBeforeReadingIt`: Caddy forwards the request and runner-api waits for the body, so there is no response within 5 s.
- `TestSandboxContainerMemoryLimitLeavesAReserveForTheHost`: the container has no memory limit.
- `TestConcurrentRunsFitWithinTheSandboxContainersLimits`: the container has neither a memory nor a process limit.

**Evidence**

- Locally: `gofmt` and `go vet -tags deploy` pass. The deployment tests run in CI only.

**Anticipated implementation**

- `deploy/Caddyfile`: `request_body { max_size 484KiB }` before `reverse_proxy`, with a comment tying it to runner-api's limit.
- `deploy/setup-host` reads the VM's memory and CPU count, and writes to `/opt/sandbox/.env`:
  - `SANDBOX_MEMORY_LIMIT`: the VM's memory less 512 MiB;
  - `SANDBOX_CONCURRENCY`: the CPU count, or fewer when that many 512 MiB runs and 128 MiB for runner-api do not fit in the memory limit. It refuses a VM too small for one run;
  - `SANDBOX_PIDS_LIMIT`: 64 processes per run, plus 256.
- `deploy/compose.yaml` gives the sandbox service `mem_limit`, `memswap_limit` and `pids_limit` from those variables, and passes `SANDBOX_CONCURRENCY` to runner-api.
- README and plan: the public instance's limits and how they are derived.
