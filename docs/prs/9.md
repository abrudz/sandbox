# Document local use and deploy the public dyalog.run instance

Closes #9. Work item 8 of [docs/plans/dyalog-runner.md](../plans/dyalog-runner.md).

## Summary

The README documents running the published image locally. `deploy/` holds the public instance:
- **`setup-host`** provisions a fresh Ubuntu 24.04 VM with Docker Engine and compose, the firewall, unattended upgrades and a daily update timer, then starts the instance. Rerunning it changes nothing.
- **Compose file:** runs the sandbox container, reachable only on loopback, behind Caddy, which serves `dyalog.run` over TLS.
- **Update timer:** pulls a newly published image and replaces the container. The old container finishes its runs in progress before it exits.

`scripts/smoke URL` checks a running instance: the page, hello world, a run killed at the time limit, and a run that cannot reach the network.

## How it was tested

- Go tests run `scripts/smoke` against fake services that fail one check each, and the integration suite runs it against the CI container.
- A CI job provisions a GitHub runner (Ubuntu 24.04) with `deploy/setup-host`, serving plain HTTP on `localhost` from a local registry, and runs the deployment tests on it as root.
- The local criterion is checked by the user on a machine with Docker. TLS for `dyalog.run` and rebooting need the VM, whose provider and size are still open; they are checked once it exists.

**Decisions in the tests**

- `scripts/smoke URL` prints one `PASS` or `FAIL` line per check, and exits non-zero when any check fails. The checks:
  - `page`: `GET /` returns the page titled `dyalog.run`.
  - `hello`: `⎕←'Hello, World!'` prints `Hello, World!` and exits 0.
  - `timeout`: a program that waits with `⎕DL` past the time limit is reported as timed out without reaching its next line.
  - `network`: a program that opens `/dev/tcp` to an outside address fails to connect.
- The fake services recognise those programs by their content (`Hello, World!`, `⎕DL`, `/dev/tcp`), so the script's programs must contain them.
- Deployment layout:
  - the compose file is `/opt/sandbox/compose.yaml`, with services `sandbox` and `caddy`;
  - the update units are `sandbox-update.service` and `sandbox-update.timer`;
  - `setup-host` takes its settings from `SITE_ADDRESS` (default `dyalog.run`) and `SANDBOX_IMAGE` (default `ghcr.io/abrudz/sandbox:latest`), and prints `No changes` when a rerun changes nothing.
- Rerunning `setup-host` must leave the sandbox container running unchanged.
- The firewall is active, denies incoming traffic by default, and allows exactly `22/tcp`, `80/tcp`, `443/tcp` and `443/udp` (HTTP/3).
- Port 8080, where the sandbox answers, listens on `127.0.0.1` only, since Docker's published ports bypass the firewall.
- Unattended upgrades refresh package lists, install upgrades and reboot when an upgrade needs it, so kernel fixes take effect.
- Docker starts at boot, and both containers have the restart policy `unless-stopped`.
- The update test:
  - **New image.** It publishes a new image (the running one with an added label) to the instance's tag, then points the local tag back at the running image, so only a pull can bring the new one in.
  - **Run in progress.** It starts an 8-second run, and a second later starts `sandbox-update.service`.
  - **Expectations.** The run must finish normally with its output, and the update must not finish before the run does. Afterwards the sandbox must run the new image and the smoke checks must pass.

**Anticipated implementation**

1. `scripts/smoke`: bash, `curl` and `jq`, one function per check.
2. `deploy/compose.yaml`:
   - **`sandbox`.** Privileged, with `127.0.0.1:8080:8080` and restart `unless-stopped`. `stop_grace_period` exceeds the time limit, so runs in progress finish. Docker's `local` log driver rotates logs.
   - **Network.** A fixed subnet, so that `SANDBOX_TRUSTED_PROXIES` can name its gateway, the address Caddy's connections arrive from.
   - **`caddy`.** On the host network, so it sees clients' real addresses over IPv4 and IPv6. It uses `deploy/Caddyfile` and a volume for its certificates.
3. `deploy/Caddyfile`: `{$SITE_ADDRESS}` proxied to `127.0.0.1:8080`.
4. `deploy/sandbox-update.service` and `.timer`:
   - Daily at 05:00 UTC, after the publish workflow's 04:23 run, with `Persistent=true`.
   - The service runs `docker compose pull`, then `docker compose up -d`, then prunes unused images.
5. `deploy/setup-host`:
   - **Packages.** It checks it runs as root, and installs `docker.io` and `docker-compose-v2` from Ubuntu only when `docker compose` is missing. It also installs `ufw` and `unattended-upgrades`.
   - **Firewall.** It allows the four ports, then enables `ufw`.
   - **Upgrades.** It configures unattended upgrades with automatic reboot.
   - **Files and services.** It installs the compose files, `.env` and units only where they differ, enables the timer, and runs `docker compose up -d`.
   - **Report.** It reports each change, or `No changes`.
6. `README.md`: what the project is, running it locally, configuration, provisioning the public instance, and development.

**Notes for review**

- The runner is not a fresh VM: Docker is preinstalled, so CI does not exercise `setup-host`'s Docker installation. The first run on the VM does.
- Caddy obtains the `dyalog.run` certificate only on the VM, once the domain's DNS points to it.
