# Tighten the jail's system call filters

Closes #42. Part of #1.

## Summary

nsjail's seccomp policy also refuses `fanotify_init`, `modify_ldt`, `vmsplice`, `name_to_handle_at` and the NUMA memory calls, and refuses sockets other than Unix and IP ones. For those calls Docker's profile is no second filter: it applies to the whole container, and allows them or allows them under `CAP_SYS_ADMIN`, which nsjail needs. `deploy/seccomp.json` drops x86_64's i386 and x32 sub-architectures, so Docker's filter refuses every i386 and x32 call, which nsjail's filter, compiled for x86_64 numbers, does not check for x32. CI checks that the profile is Moby's with only these recorded changes.

## How it was tested

Integration tests make each call from a run through `⎕NA`; a test compares `deploy/seccomp.json` with Moby's profile at the revision `THIRD_PARTY_NOTICES` records.

**Decisions in the tests**

- Each call goes through the C library's `syscall`, with x86_64 numbers. The arguments are ones the kernel accepts from an unprivileged process, or rejects with an error other than EPERM, so EPERM comes only from a seccomp filter: `fanotify_init` with `FAN_REPORT_FID`, which unprivileged processes may use since Linux 5.13; `modify_ldt` reading no bytes; `vmsplice` and `name_to_handle_at` on descriptor -1.
- A run-time result cannot tell which filter refused a call. Docker's profile already refuses `mbind`, `migrate_pages` and `move_pages` (they need `CAP_SYS_NICE`), and the kernel refuses `AF_PACKET` and `AF_KEY` sockets to a process without capabilities, and Docker's profile refuses `AF_ALG`; those subtests pass already and guard the result. `fanotify_init`, `modify_ldt`, `vmsplice`, `name_to_handle_at` and `AF_NETLINK` reach the kernel today. `AF_TIPC` reaches it too, and fails or succeeds by whether the kernel can load its module.
- x32 calls are not tried at run time: a kernel built without x32, as Ubuntu's generic kernel is, refuses them whatever the filters. The profile comparison covers the `archMap` change instead.
- The comparison reads Moby's revision from `THIRD_PARTY_NOTICES`, so the notice and the profile cannot drift apart, and fetches that revision's `seccomp/default.json` from `moby/profiles`. It applies the recorded changes to Moby's profile, sorts every rule's names so that where `pivot_root` sits does not matter, and compares the result with `deploy/seccomp.json`. It needs no container, so it also runs locally.

**Expected failures**

- `TestRarelyNeededSystemCallsFailWithEPERM`: `fanotify_init` returns a descriptor, `modify_ldt` returns 0, `vmsplice` and `name_to_handle_at` fail with another errno. The NUMA subtests pass.
- `TestSocketsOtherThanUnixAndIPFailWithEPERM`: `AF_NETLINK` returns a descriptor; `AF_TIPC` does not fail with EPERM. The `AF_PACKET`, `AF_KEY` and `AF_ALG` subtests pass.
- `TestSeccompProfileIsMobysWithOnlyTheRecordedChanges`: the x86_64 entry of `archMap` still lists `SCMP_ARCH_X86` and `SCMP_ARCH_X32`.
- `TestUnixAndIPSocketsOpen` passes.
