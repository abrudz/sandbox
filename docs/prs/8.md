# Publish the image automatically when Dyalog updates

Closes #8. Work item 7 of [docs/plans/dyalog-runner.md](../plans/dyalog-runner.md).

## Summary

`.github/workflows/publish.yml` publishes `ghcr.io/abrudz/sandbox:latest` and `ghcr.io/abrudz/sandbox:<dyalog-version>`. It runs on every push to `main`, and daily when the digest of `docker.io/dyalog/dyalog:latest` differs from the one the published image was built from. Every image is built from the upstream image by digest and tested with the integration and UI suites before anything is pushed; a failing suite fails the workflow and publishes nothing. The image's OCI labels record the upstream digest, the Dyalog version and the commit, and `GET /api/v1/version` reports the same three values.

## How it was tested

A Go unit test covers the version endpoint's new fields. Integration tests in CI compare the running image's labels with `/api/v1/version` and with the commit under test. The workflow's publishing, skipping and failure paths are verified with `workflow_dispatch` runs, as the issue specifies; each cycle below links its runs.

**Decisions in the tests**

- `/api/v1/version` keeps the plan's field names: `dyalogVersion`, `imageDigest` and `commit`. `imageDigest` is the digest of the upstream `docker.io/dyalog/dyalog:latest` the image was built from. The published image's own digest is only known after it is built, so the image cannot report it.
- The labels are the OCI annotations:
  - `org.opencontainers.image.version` for the Dyalog version;
  - `org.opencontainers.image.base.name` (`docker.io/dyalog/dyalog:latest`) and `org.opencontainers.image.base.digest` for the upstream image;
  - `org.opencontainers.image.revision` for the commit.
- The digest must be `sha256:` and 64 hex digits, the commit 40 hex digits, and the version dotted numbers.
- The image under test must carry the commit that CI checked out, so CI tests the same build that publishing uses.

**Expected failures**

- `TestGetVersionReportsTheUpstreamDigestAndCommit`: `imageDigest` and `commit` are absent from the response.
- `TestVersionReportsTheImageLabels`: the image has none of the labels, and the API reports empty `imageDigest` and `commit`.
- `TestImageIsBuiltFromTheCommitUnderTest`: the image has no revision label.

**Anticipated implementation**

1. `image/Containerfile`:
   - Build from `ARG DYALOG_IMAGE`, which defaults to `docker.io/dyalog/dyalog:latest`.
   - Write `DYALOG_DIGEST` and `COMMIT` build arguments to files under `/usr/share/sandbox`, next to `dyalog-version`, and to the labels.
2. `cmd/runner-api` reads those files into `Options`; the version handler reports them.
3. `scripts/build-image`:
   - Resolve the upstream digest unless one is given.
   - Build `FROM docker.io/dyalog/dyalog@<digest>` with the digest, the commit and the labels.
   - Add the version label, which is only known once the image has run `dyalogscript`.
4. `.github/workflows/image.yml`, a reusable workflow:
   - Build with the script, start the container, and run the integration and UI suites.
   - When asked to publish, and only after every step has passed, log in to GHCR and push both tags.
   - `ci.yml` calls it without publishing on every push.
5. `.github/workflows/publish.yml`, on pushes to `main`, a daily schedule and `workflow_dispatch`:
   - A first job resolves the upstream digest and, on the daily schedule, compares it with the published image's `base.digest` label.
   - It then calls `image.yml` to publish, or stops.
   - The dispatch inputs are a daily-mode switch and an upstream image override. A run with an override never publishes.
   - Runs are serialised so two publishes cannot interleave.

**Notes for review**

- GitHub runs `workflow_dispatch` only for workflows present on the default branch. If it refuses to dispatch `publish.yml` from this branch, the daily-mode and failure-path runs happen right after merge, and their results are added to this PR as a comment.
- A new GHCR package is private. After the first publish, the package's visibility has to be set to public once, in its settings on GitHub, for `docker pull` to work without logging in.
