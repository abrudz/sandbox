# Isolate each run's network, filesystem, resources and privileges

Closes #5. Work item 4 of [docs/plans/dyalog-runner.md](../plans/dyalog-runner.md).

## Summary

Every run gets its own cgroup with a memory limit and no swap, a CPU limit and a process limit, and a seccomp policy that refuses the system calls a sandboxed program has no use for. The limits come from the environment (`SANDBOX_MEMORY`, `SANDBOX_CPUS`, `SANDBOX_PIDS`) with the plan's defaults of 512 MiB, one CPU and 64 processes; the interpreter's workspace (`MAXWS`) is half the memory limit. An out-of-memory event ends the whole run, and the CPU limit is enforced over 100 ms periods; both come from a small patch to nsjail. The tests also cover the isolation nsjail's namespaces already provide: no network, a read-only filesystem outside `/tmp` and the home directory, 16 MiB tmpfs mounts, nothing kept between runs, an unprivileged user without capabilities that sees only its own processes, and concurrent runs that cannot see each other.

## How it was tested

Unit tests for reading the limits run in the dev container with `go test ./...`. Integration tests run in CI against the CI container and against containers started with each new variable (plan, Development environment); each cycle below links its CI run.

**Decisions in the tests**

- New variables: `SANDBOX_MEMORY` (bytes, or a number with `K`, `M` or `G` in powers of 1024), `SANDBOX_CPUS` (CPU-seconds per second, for example `0.5`) and `SANDBOX_PIDS`. `MAXWS` is derived as half the memory limit rather than set separately, so the interpreter reports `WS FULL` before the cgroup kills it whatever memory limit is chosen. The tmpfs size stays fixed at 16 MiB, as in the plan's table.
- The network test asks bash to connect to 1.1.1.1:80 and requires "Network is unreachable", not merely a failure, so a test that cannot connect for another reason does not pass.
- The fork-bomb criterion is tested with a bounded loop that starts 500 sleeping processes and then counts the processes it can see using shell builtins only, so the count works once no more processes can start. An unbounded bomb in the RED run would have had only nsjail's per-user process rlimit (1024) between it and the CI runner.
- The memory tests have a child of `⎕SH` buffer 1 GB (or 200 MB with `SANDBOX_MEMORY=128M`) through `tail` and print the child's exit status; 137 means SIGKILL. `⎕SH` raises no error when its child is killed, so the status is printed rather than caught.
- The CPU tests compare `userTimeMs + sysTimeMs` with `wallTimeMs`, with a lower bound that fails the test if the busy loops did not run.
- The `⎕NA` test calls `unshare(CLONE_NEWUSER)` and reads `errno` through `__errno_location` and `memcpy`. The kernel refuses the call in a multithreaded process such as the interpreter with EINVAL (22); a seccomp filter runs before the kernel sees the call, so EPERM (1) can only come from the policy.
- The concurrency test starts a run that writes marker files and a `sleep 5.000123`, waits until that sleep is visible in the container, then checks from a second run that neither marker exists and no process command line contains `5.000123`. It uses a container of its own.

**Expected failures**

- The config unit tests: the new limits read as zero and invalid values are accepted.
- `TestAChildPastTheMemoryLimitIsKilledAndTheServiceKeepsServing` and `TestSandboxMemorySetsTheMemoryLimit`: the child is not killed (`status 0`).
- `TestProcessCreationStopsAtTheProcessLimit` and `TestSandboxPidsSetsTheProcessLimit`: 503 and 103 processes are visible.
- `TestTwoBusyProcessesShareOneCPU`: 4021 ms of CPU time in 2022 ms. `TestSandboxCpusSetsTheCPULimit`: 2020 ms in 2021 ms.
- `TestBlockedSystemCallThroughQuadNAFailsWithEPERM`: `¯1 22`; the kernel, not a policy, refuses the call.
- `TestSandboxMemorySetsTheWorkspaceToHalfTheMemoryLimit`: `⎕WA` is 267312576, from the fixed `MAXWS=256M`.
- Passing already, through nsjail's namespaces and the configuration from #3: the network, filesystem, tmpfs, persistence, `WS FULL`, privilege and concurrency tests. They guard that isolation from now on.

**Evidence**

**Anticipated implementation order**

1. `config.FromEnv`: `SANDBOX_MEMORY`, `SANDBOX_CPUS` and `SANDBOX_PIDS` with defaults and validation; `Workspace()` returns half of `Memory`.
2. `image/nsjail.cfg`: `use_cgroupv2: true`; a seccomp policy in Kafel (nsjail 3.6's bundled revision) that answers EPERM for namespace and mount system calls (`unshare`, `setns`, `mount`, `umount`, `pivot_root`, `chroot`, the new mount API), `clone` with any namespace flag, tracing and cross-process memory access, `bpf`, `perf_event_open`, key management, `userfaultfd`, `io_uring`, module and kexec loading, clock and swap changes, and similar; and ENOSYS for `clone3`, whose flags a filter cannot read, so that the C library falls back to `clone`. `MAXWS` moves out of the file.
3. `internal/sandbox.Nsjail`: per-run flags `--cgroup_mem_max`, `--cgroup_mem_swap_max 0`, `--cgroup_pids_max`, `--cgroup_cpu_ms_per_sec` and `--env MAXWS=...` from the limits.
4. `cmd/runner-api`: passes the new limits to the executor and logs them at start-up.

### Cycle 2: GREEN

**Changes**

- `internal/config`: `SANDBOX_MEMORY` (bytes, or a number with `K`, `M` or `G`), `SANDBOX_CPUS` (a positive number) and `SANDBOX_PIDS` (a positive integer), with defaults of 512 MiB, 1 and 64 and errors that name the variable. `Workspace()` is half of `Memory`.
- `image/nsjail.cfg`: `use_cgroupv2: true`, and a Kafel seccomp policy. It answers EPERM for `unshare`, `setns`, `mount`, `umount`, `pivot_root`, `chroot`, the new mount API, `clone` with any namespace flag, `ptrace`, `process_vm_readv`/`writev`, `pidfd_getfd`, `bpf`, `perf_event_open`, `userfaultfd`, `io_uring_*`, key management, module and kexec loading, `open_by_handle_at`, `lookup_dcookie`, `quotactl`, `acct`, `syslog`, `vhangup`, swap, `reboot`, `iopl`, `ioperm` and clock changes. `clone3` answers ENOSYS so the C library falls back to `clone`. `MAXWS` is no longer set here.
- `internal/sandbox/nsjail.go`: per-run flags `--cgroup_mem_max`, `--cgroup_mem_swap_max 0`, `--cgroup_pids_max`, `--cgroup_cpu_ms_per_sec` (CPUs × 1000, at least 1) and `--env MAXWS=<n>K`, with the unit explicit because Dyalog reads a bare size as KiB.
- `image/run`: passes `MAXWS` on `dyalogscript`'s command line. In script mode Dyalog does not apply the `MAXWS` environment variable (observed on 20.0 locally and 21.0 in CI), but it does apply a setting given before the script.
- `image/nsjail.patch`, applied in the nsjail build stage, changes nsjail's `cgroup2.cc` in two places marked "Local change":
  - it writes `memory.oom.group=1`, so one out-of-memory kill takes every process in the run;
  - it writes `cpu.max` with a 100 ms period, as Docker does, instead of 1 s.
  `THIRD_PARTY_NOTICES` records the modification, as the Apache License requires.
- `cmd/runner-api`: passes the new limits to the executor and logs them all at start-up.

**Test changes in this cycle**

- The process-limit tests fork from Perl instead of `dash`. `⎕SH` runs `dash`, which exits as soon as a fork fails, so under a real process limit the RED version never reached its count.
- The two memory tests expect an out-of-memory event to end the whole run (SIGKILL, not timed out, the child's status never printed), and the service to keep serving. This follows the decision recorded below. `TestSandboxMemorySetsTheMemoryLimit` gains a control: the same 200 MB child completes under the default 512 MiB limit.
- The isolation tests report the whole run (exit code, signal, timeout, wall time, stdout, stderr) when their output differs.

**Decision: an out-of-memory event ends the whole run**

With only `memory.max`, the kernel killed the child that exhausted the limit. But in 7 of 12 CI trials a second out-of-memory event followed, raised by `head` still writing into the pipe before the first victim's memory was freed. That event chose the next-largest process, the interpreter, and twice the `dyalogscript` wrapper as well. The kernel's own reports showed this.

Protecting the interpreter with `oom_score_adj` would need every child to raise its own score, which `⎕SH` could be made to do but `⎕SHELL` and `⎕NA` could not. The user chose deterministic behaviour instead: `memory.oom.group` kills the whole run on the first event. The response reports SIGKILL, and the program does not see its child's failure.
