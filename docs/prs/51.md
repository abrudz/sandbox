# Make .NET available to runs

Closes #51. Part of #1.

## Summary

The jail mounts the .NET runtime that the base image installs at `/opt/dotnet`, read-only, and sets `DOTNET_ROOT`, so `⎕USING` and .NET classes work in a run. runner-api limits each run's .NET heap to a quarter of its memory limit, beside the workspace's half, so a .NET allocation past it is an exception the program can trap rather than a kill of the whole run. The runtime opens no diagnostics channel.

## How it was tested

Integration tests call .NET from a run, allocate past the heap limit, read the limit the garbage collector reports under two memory limits, list `/tmp` after loading .NET, time a run that loads it, and try to write to the runtime's files.

**Decisions in the tests**

- The .NET call is `Math.Sqrt 16`: `Math.Sqrt` has a single overload, so the result does not depend on how the interpreter chooses between overloads. `2↑2250⌶0` is `1 1` when the interface is configured for .NET and the bridge loaded.
- The allocation is a `StringBuilder` with a capacity of 100 million characters, which allocates 200 MB at once and stays a .NET object, where an array returned to APL would be converted into the workspace. 200 MB is more than a quarter of the default 512 MiB limit and less than the limit, so only the heap limit can refuse it. The run traps `EXCEPTION` (90), prints the exception's type and then a line of its own, and must exit with status 0.
- The heap limit is read from the garbage collector, as `TotalAvailableMemoryBytes` of `GC.GetGCMemoryInfo`, which is the hard limit when one is set. It must be 128 MiB under the default memory limit and 64 MiB in a container started with `SANDBOX_MEMORY=256M`. 128M would leave a run 32 MiB beside its workspace and .NET heap, too little to load the runtime.
- Without diagnostics disabled, the runtime creates `dotnet-diagnostic-*` and `clr-debug-pipe-*` in `/tmp` as it starts. The run lists `/tmp` with `⎕SH` after a .NET call, and the test first requires the call's output, so that it cannot pass on a run where .NET never started.
- The time bound, 3 s for a whole run that loads .NET, leaves the default 10 s limit most of a run's time.
- `/opt/dotnet/marker` joins the paths a run must fail to write. It fails before this change because the directory does not exist in the jail; after it, because the mount is read-only.

**Expected failures**

- `TestARunCallsADotNetMethod`, `TestARunThatLoadsDotNetFinishesInUnder3Seconds`, `TestADotNetAllocationPastTheHeapLimitThrowsAnExceptionTheRunCanTrap`, `TestTheDotNetHeapLimitIsAQuarterOfTheMemoryLimit`, `TestARunUsingDotNetOpensNoDiagnosticsChannel`: the runtime is not visible in the jail, so the bridge does not load and every .NET name fails.
- `TestRunCannotWriteOutsideTmpAndHome` passes.

**Evidence**

- Locally: `gofmt` and `go vet -tags integration` pass. The integration tests run in CI only.

**Anticipated implementation**

- `image/nsjail.cfg`: a read-only bind mount of `/opt/dotnet`, `DOTNET_ROOT=/opt/dotnet`, and `DOTNET_EnableDiagnostics=0`.
- `internal/sandbox/nsjail.go`: `DOTNET_GCHeapHardLimit` for each run, a quarter of its memory limit, in hexadecimal as the runtime reads it.
- Whatever further runtime settings the runtime needs to start under the jail's 4 GiB address-space and 16 MiB file-size limits, found in CI, each with its reason in `image/nsjail.cfg`. `DOTNET_EnableWriteXorExecute=0` is the likely one.
- README and plan: .NET in runs, the heap limit beside the workspace, and the settings.
