# Close the kernel module autoload paths open to a run

Closes #57. Part of #1.

## Summary

A run can no longer make the kernel load a module. The jail's seccomp policy already refused sockets in families other than Unix, IPv4 and IPv6; it now also refuses IP sockets with a protocol other than the default, TCP and UDP, `socketpair` in any family but Unix, the socket ioctls that load `8021q` and `bridge`, and the `TCP_ULP` socket option. `setup-host` installs a modprobe configuration that refuses the socket protocol and family modules the host does not use, so that a gap in either seccomp filter cannot load them. README says not to run the container with `--privileged`, which turns off the seccomp profile that refuses x32 system calls.

The protocol and `TCP_ULP` rules, their tests and the README warning come from Neil Kirsopp's review (branch `harden-run-isolation` of cursork/sandbox), which also suggested the modprobe configuration.

## How it was tested

Integration tests make each refused call from a run through `⎕NA` and require EPERM, which the kernel never answers for these calls with the arguments used; others require that TCP, UDP and Unix socket pairs still open. Deployment tests ask modprobe, after `setup-host`, what it would do to load each refused module and each module Docker uses.

**Decisions in the tests**

- Every refused call uses arguments for which the kernel answers something other than EPERM, or succeeds, so EPERM comes only from the policy. The comments name the kernel's other answers: EPROTONOSUPPORT or ESOCKTNOSUPPORT for a missing protocol; EOPNOTSUPP or EAFNOSUPPORT from `socketpair`; EFAULT or ENOPKG for the ioctls with a null argument; ENOENT or ENOTCONN for `TCP_ULP`. The bridge requests that add or delete a bridge are not tried, because the kernel answers them EPERM itself for a caller without `CAP_NET_ADMIN`.
- The protocol cases are those whose modules the kernel loads (SCTP, DCCP, UDP-Lite, L2TP) and MPTCP, which is built in, so that the test holds the rule to an allowlist.
- `socketpair` gets a real two-element output array through `⎕NA`, so the kernel reaches the socket creation that loads modules.
- The new socket tests use `systemCall`, as the existing socket tests do, where one system call is enough, and a `withErrno` helper where a run needs a socket first.
- The deployment tests ask `modprobe --dry-run --verbose` rather than loading anything, so they hold whether or not the runner's kernel has a module's file. A refused module's plan is `install /bin/false`. `bridge`, `veth`, `overlay`, `br_netfilter` and `nf_nat` must still load, so that the configuration cannot break Docker after a reboot.

**Expected failures**

- `TestIPSocketsWithAProtocolOtherThanTCPOrUDPFailWithEPERM`: every case opens a socket or fails with an error other than EPERM.
- `TestSocketPairsOtherThanUnixOnesFailWithEPERM`: every case fails with EOPNOTSUPP, EAFNOSUPPORT or EPROTONOSUPPORT, or succeeds. (The run showed otherwise for the IP cases; see the evidence.)
- `TestSocketIoctlsThatLoadAModuleFailWithEPERM`: both requests fail with EFAULT or ENOPKG.
- `TestSettingATCPUpperLayerProtocolFailsWithEPERM`: ENOENT or ENOTCONN.
- `TestModprobeRefusesTheSocketModulesTheHostDoesNotUse`: modprobe would load each module, or finds no such module.
- The other new tests pass already.

**Evidence**

- Locally: `gofmt` and `go vet` (with `-tags integration` and `-tags deploy`) pass. The tests run in CI only.
- CI run [45838158284](https://github.com/abrudz/sandbox/actions/runs/45838158284) on `d5335e4`, on the runner's kernel 7.0.0-1020-azure:
  - `TestIPSocketsWithAProtocolOtherThanTCPOrUDPFailWithEPERM` fails in every case. SCTP, UDP-Lite, L2TP, MPTCP and SCTP over IPv6 sockets open (descriptor 16), so a run made the kernel load `sctp` and `l2tp_ip`; DCCP fails with ESOCKTNOSUPPORT, as this kernel has no DCCP.
  - `TestSocketPairsOtherThanUnixOnesFailWithEPERM` fails for AF_TIPC alone, with EAFNOSUPPORT. The IP cases already fail with EPERM: Docker's seccomp profile, which `deploy/seccomp.json` keeps, allows `socketpair` in Unix and TIPC only. TIPC is the family the jail is open to through `socketpair`.
  - `TestSocketIoctlsThatLoadAModuleFailWithEPERM` fails with EFAULT for both requests; `TestSettingATCPUpperLayerProtocolFailsWithEPERM` with ENOENT.
  - `TestModprobeRefusesTheSocketModulesTheHostDoesNotUse` fails for every module: modprobe would load each, or finds no DCCP module, except `8021q` and `qrtr`, for which it plans nothing.
  - The other new tests, the rest of the integration and deployment suites, the 52 UI tests, lint and the unit tests pass.
- Test corrections after this run:
  - `TestSocketPairsOtherThanUnixOnesFailWithEPERM`: the comment says that Docker's profile already refuses the IP cases, and that the jail's policy refuses them too so as not to depend on it. The cases are unchanged.
  - `TestModprobeRefusesTheSocketModulesTheHostDoesNotUse`: modprobe plans nothing for a module the kernel already has, built in or loaded, as `8021q` and `qrtr` appear to be on this runner, whatever its configuration says. The test now requires every module's `install ... /bin/false` line in modprobe's effective configuration (`modprobe --showconfig`), and the `install /bin/false` plan for each module not yet in the kernel; it logs those already in the kernel, which only the seccomp policy keeps from a run.

### Cycle 2: GREEN

**Changes**

- `image/nsjail.cfg`, in Neil Kirsopp's commit: the policy refuses `socket` in IPv4 and IPv6 with a protocol other than 0 (the default), 6 (TCP) and 17 (UDP), and `setsockopt` with level 6 (`SOL_TCP`) and option 31 (`TCP_ULP`).
- `image/nsjail.cfg`, on top of it: the policy refuses `socketpair` in every family but Unix, and `ioctl` with the six bridge requests (`0x8940`, `0x8941`, `0x89a0` to `0x89a3`) and the two VLAN requests (`0x8982`, `0x8983`). The comment says which socket calls fail and why, and that `TCP_ULP` loads a module only under `CAP_NET_ADMIN` in the host's namespace, so it is refused to keep runs from protocols the host has already loaded, not to stop a load.
- `deploy/60-sandbox-modules.conf`, installed by `setup-host` as `/etc/modprobe.d/60-sandbox-modules.conf`: `install <module> /bin/false` for the IP protocol modules (SCTP, DCCP, L2TP, SMC), the address family modules (`af_key`, AppleTalk, ATM, AX.25, Bluetooth, CAIF, CAN, IEEE 802.15.4, KCM, LLC2, NET/ROM, NFC, Phonet, QRTR, RDS, ROSE, RxRPC, TIPC, X.25) and `8021q`. modprobe reads the file at every load, so nothing needs reloading.
- README: `setup-host`'s list names the modprobe configuration; `--privileged` must not replace the container's options, because without the seccomp profile x32 calls pass the jail's own filter. The plan says the same, and lists the new refusals.
- `kernel.modules_disabled=1`, also suggested, is not set: it cannot be undone without a reboot, and it refuses the modules Docker and netfilter load on demand when compose creates or recreates networks.

**Evidence**

- Locally: `gofmt`, `go vet` (with `-tags integration` and `-tags deploy`) and `bash -n deploy/setup-host` pass.
- CI run [45839581698](https://github.com/abrudz/sandbox/actions/runs/45839581698) on `3a27671`: every job passes. Every refused socket call fails with EPERM, including `socketpair` in TIPC, the two ioctls and `TCP_ULP`; TCP, UDP and Unix sockets and Unix socket pairs open. After `setup-host`, modprobe's configuration refuses every listed module, and its plan for each one not in the kernel is `install /bin/false`; `8021q` and `qrtr` are already in the runner's kernel, so for them only the seccomp policy applies. Docker's modules still load, rerunning `setup-host` changes nothing, and the rest of the integration and deployment suites, the 52 UI tests, lint and the unit tests pass.
