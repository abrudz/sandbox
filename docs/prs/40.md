# Refuse to start outside a private cgroup namespace

Closes #40. Part of #1.

## Summary

The entry point exits with an error, before it touches the cgroup filesystem, unless the container is in a cgroup namespace of its own. Its cgroup changes assume that the root of its namespace is the container's own cgroup; in the host's namespace that root is the host's. `deploy/compose.yaml`, the README's `docker run`, CI and the integration tests all ask for a private cgroup namespace explicitly rather than relying on Docker's default.

## How it was tested

An integration test starts the image in the host's cgroup namespace on the CI runner, and a deployment test checks the deployed container's mode.

**Decisions in the tests**

- The integration test starts the image with the usual flags plus `--cgroupns host`, which overrides any earlier `--cgroupns`. It waits up to 15 s for the container to exit, then requires a non-zero exit status and "cgroup namespace" in its log.
- The entry point's first write is `mkdir init` at the root of its cgroup namespace. In the host's namespace that is the host's `/sys/fs/cgroup/init`, which the test, running on the host, checks does not exist before or after.
- In RED the entry point does run in the host's namespace on the CI runner: it creates `/sys/fs/cgroup/init` there and enables controllers at the host's root, which a systemd host has enabled already. The runner is discarded after the job, and every other container in the suite has a private namespace, so nothing else sees the change.
- `TestSandboxContainerHasAPrivateCgroupNamespace` passes already, because Docker's default on cgroup v2 is private. It guards the deployment against a daemon whose default is the host's namespace, once `compose.yaml` asks for private explicitly.

**Expected failures**

- `TestTheContainerRefusesToStartInTheHostsCgroupNamespace`: the container keeps running, its log does not mention the cgroup namespace, and `/sys/fs/cgroup/init` appears on the host.

**Evidence**

- Locally: `gofmt` and `go vet` (with `-tags integration` and `-tags deploy`) pass. The integration and deployment tests run in CI only.
- CI run [45624843148](https://github.com/abrudz/sandbox/actions/runs/45624843148) on `5ea8d00`:
  - lint, the unit tests, the UI tests and the deployment tests pass, `TestSandboxContainerHasAPrivateCgroupNamespace` among them;
  - of the integration tests, only `TestTheContainerRefusesToStartInTheHostsCgroupNamespace` fails: 15 s after starting, the container is `running 0` and has logged only runner-api's start-up line, and the entry point has created `/sys/fs/cgroup/init` in the runner's own cgroup hierarchy.

**Anticipated implementation**

- `image/entrypoint`: before the remount, exit with an error naming the cause unless `/proc/self/cgroup` is exactly `0::/`. That also refuses a host with cgroup v1, whose `/proc/self/cgroup` has other lines.
- `deploy/compose.yaml`: `cgroup: private` for the sandbox service.
- `README.md`, `.github/workflows/image.yml` and `runFlags` in the integration tests: `--cgroupns private`.
- The plan's container section: the private cgroup namespace and the check.
