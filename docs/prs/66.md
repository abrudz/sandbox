# Limit the size of a permalink the page decodes

Closes #66. Part of #1.

## Summary

The page stops inflating a permalink once its fields pass 1 MiB, and opens a permalink with at most 256 arguments: sixteen times runner-api's default limit on code plus input (64 KiB) and its limit on arguments (16), so any permalink a run could accept still opens unchanged. A permalink over either limit, in either of TIO's formats, opens nothing and says why; nothing is truncated. A crafted fragment can no longer make the page inflate gigabytes or create a million argument fields.

## How it was tested

Unit tests of `web/codec.js` decode permalinks at runner-api's limits, just under 1 MiB, past it, and with 256 and 257 arguments, and count the bytes pako inflates for a 16 MiB permalink. Browser tests open an oversized permalink and ones with 300 arguments, in each format, and check the message and that no field is set and nothing runs.

**Decisions in the tests**

- The oversized permalink holds 16 MiB of code, which deflates to a few kilobytes. To see that decoding stops, the test swaps in a pako whose `Inflate` and `inflateRaw` record how many bytes they have inflated, whichever the codec uses, and allows 1 MiB and one 64 KiB chunk.
- The limits are tested at their edges: 256 arguments open and 257 do not; fields just under 1 MiB open.
- The browser tests build permalinks with the page's own codec, run in the test process, and the first format by hand. "Opens nothing" means a message matching the reason, an empty Code field, no argument field, and an empty Output, since nothing runs.

**Expected failures**

- `a permalink whose fields inflate past 1 MiB is refused, and decoding stops soon after`: the permalink opens, after inflating all 16 MiB.
- `a permalink with 256 arguments opens and one with 257 is refused`: 257 arguments open.
- Both browser tests: the permalinks open, with every argument field, and the page runs them.
- The other new unit tests pass already.

**Evidence**

- Locally: `node --check` passes, and `node --test test/ui/codec.test.js` fails exactly the two unit tests above. The browser tests run in CI only.
- CI run [45967883167](https://github.com/abrudz/sandbox/actions/runs/45967883167) on `797d0ef`: exactly the four tests fail. In the lint and unit job, the 16 MiB permalink opens after 1.5 s of inflating, and 257 arguments open; in the browser suite, both permalinks open, with every argument field. The other new unit tests, the other 52 browser tests and the integration and deployment suites pass.

### Cycle 2: GREEN

**Changes**

- `web/codec.js`: `maxPermalinkBytes` (1 MiB) and `maxPermalinkArguments` (256). `inflate` streams through pako's `Inflate`, counting its output, and throws a `RangeError` once it passes 1 MiB, so a crafted permalink is never inflated in full. `parsePermalink` throws a `RangeError` for more than 256 arguments before decoding any field to text. `checkFirstFormat` applies both limits to the first format's decoded fields.
- `web/frontend.js`: `decodePermalink` decodes either format to a language, the four fields and the arguments, checking the limits, before `hashToState` touches the page; in the first format it counts the arguments before decoding them. A `RangeError` shows "The permalink was not opened: " and its reason; any other error, now including bad base64 in the first format, shows "The permalink could not be decoded." Either way no field changes and nothing runs.
- Plan: the frontend section states the limits.
- Test change: the first-format part of the arguments test builds its link with `firstFormatLink`, from #67's tests, which writes base64 without padding, as TIO did; its own padded base64 would have cut each argument short at the page's `=` separator. The RED run never reached that part, which comes after the new-format part that failed first.
