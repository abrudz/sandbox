# Treat NAME=value arguments as configuration parameters

Closes #31. Part of #1.

## Summary

An argument `NAME=value` sets the interpreter's configuration parameter `NAME` for the run, as it does on TIO, where `apl-dyalog` passes the arguments to the interpreter's command line. A program reads it with `2⎕NQ#'GetEnvironment' 'NAME'`. Every other argument reaches the program as before, through `GetCommandLineArgs`. The service's `MAXWS` applies whatever the arguments say.

## How it was tested

Integration tests in CI against the container, as for #7.

**Decisions in the tests**

- The value under test is ``a  b 'c' "d" =e \f $HOME;`id` *``: two spaces in a row, both kinds of quote, `=`, a backslash, a variable, a command substitution and a glob.
- The program arguments under test are `x y`, `FOO=bar`, `-z`, `1=2` and `=e`. `1=2` and `=e` contain `=` but have no valid name before it, so they stay program arguments. `-z` stays a program argument, not an interpreter option. The program prints whether `FOO=bar` is among its arguments, then its last four.
- With the default memory limit of 512 MiB, the service's `MAXWS` is 256 MiB. The program prints whether `⎕WA` exceeds 128 MB, which it would not under `MAXWS=64M`.

**Expected failures**

- `TestRunSetsAConfigurationParameterFromANameValueArgument` and `TestRunKeepsAConfigurationParameterValueAsGiven`: `FOO` is not set, so the program prints an empty line.
- `TestRunPassesOnlyArgumentsOtherThanNameValueToTheProgram`: `FOO=bar` is a program argument, so the program prints `1`, and `FOO=bar` is among the last four.
- `TestRunKeepsTheServicesWorkspaceSizeWhenAnArgumentSetsMAXWS` passes, because `MAXWS=64M` is only a program argument today. It holds the implementation to passing the service's `MAXWS` first.

**Evidence**

- Locally, with `dyalogscript` 20.0 outside the jail: `dyalogscript s.apls FOO=bar` leaves `FOO` unset and passes `FOO=bar` to the program, while `dyalogscript FOO=bar s.apls` sets it.
- CI run [45409223219](https://github.com/abrudz/sandbox/actions/runs/45409223219) on `9bd804e`: lint, the unit tests, the 52 UI tests and the Deployment job pass. Of the integration tests, exactly the three expected ones fail:
  - `TestRunSetsAConfigurationParameterFromANameValueArgument` and `TestRunKeepsAConfigurationParameterValueAsGiven`: the output is an empty line, `"\r"`.
  - `TestRunPassesOnlyArgumentsOtherThanNameValueToTheProgram`: the output is `1`, `FOO=bar`, `-z`, `1=2`, `=e`.
  - `TestRunKeepsTheServicesWorkspaceSizeWhenAnArgumentSetsMAXWS` and `TestRunPassesArgumentsToTheProgram` pass.

**Anticipated implementation**

`image/run` splits the arguments. Each argument that matches `^[A-Za-z_][A-Za-z0-9_]*=` goes before the script, after the service's `MAXWS`; the rest go after the script, as now. Two constraints, both observed locally with `dyalogscript` 20.0:

- `dyalogscript` evaluates the parameters before the script as shell words: `dyalogscript 'FOO=a b' s.apls` sets `FOO` to `a` and fails with "ws not found". Each parameter is therefore quoted with `printf %q`, which `dyalogscript` 20.0 turns back into the value unchanged.
- When a parameter is given twice, the interpreter takes the first, so the service's `MAXWS` comes first.

The alternative is to set `NAME=value` as an environment variable of the run, which `GetEnvironment` also reads. It depends on no detail of `dyalogscript`, but in script mode some parameters, `MAXWS` among them, take effect only on the command line, which is where TIO puts them.

The plan's API contract and the README describe the new meaning of `args`.
