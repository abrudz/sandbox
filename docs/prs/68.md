# Pin the registry image CI's deployment job starts

Closes #68. Part of #1.

## Summary

CI's deployment job starts the registry the public instance's stand-in pulls from as `docker.io/library/registry:2.8.3@sha256:a3d8aaa6…`, the digest the tag `2` named, instead of the floating tag `registry:2`. Every image a workflow starts is now named by digest, or is the image the job built itself.

## How it was tested

A unit test reads every `docker run` in the workflows and requires a digest on the image it starts, unless a shell variable names it, which is the image the job built and checks by ID. The deployment job then runs with the pinned registry.

**Decisions in the tests**

- The image is the last word of a `docker run` command, with continuation lines joined: no workflow passes a container a command. A word that starts with `$` is a shell variable, which in every workflow names the image the job built itself and has checked by ID.

**Expected failures**

- `TestEveryImageAWorkflowStartsIsNamedByDigest`: `docker.io/library/registry:2` in `ci.yml`.

**Evidence**

- Locally: `gofmt` and `go vet` pass, and `go test ./test/workflows/` fails exactly this test: "ci.yml: docker.io/library/registry:2 is not named by digest".
