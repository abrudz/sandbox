# Bound what a run request can hold outside its run

Closes #37. Part of #1.

## Summary

runner-api counts a client's run requests from the moment their headers arrive, and limits how many request bodies are read at once, so slow uploads cannot pile up in memory before any limit applies. A request must arrive in full within 15 s, and an idle connection closes after 3 minutes. A run's slot is freed when the run ends, and a response the client does not read is abandoned after 10 s. Only whitespace may follow a body's JSON value, so the server always reads the body to its end and notices when the client disconnects.

## How it was tested

Go unit tests against the handler, and against its HTTP server on a loopback port for timeouts and disconnects; one integration test checks the 15 s read timeout of the image's server.

**Decisions in the tests**

- The timeouts are `Options`, so the unit tests use a few hundred milliseconds. The production values are constants in `cmd/runner-api`; the integration test checks the 15 s read timeout through the image's server. The 3 minute idle and 10 s response timeouts are covered by the unit tests' mechanism only.
- The idle timeout is longer than Caddy's default keep-alive for upstream connections (2 minutes). The other way round, Caddy can send a request on a connection runner-api is closing, and Caddy does not retry a POST.
- A stalled upload is a body read from a pipe. A pipe write returns only once the handler has read it, so the test knows the request is being read before it sends the next one.
- Too many bodies being read at once gets 503, because the service is busy; a client over its own limit gets 429.
- A client that does not read has a 4 KiB receive buffer and gets a 16 MiB response, more than a loopback connection buffers, so the server's write blocks.
- `TestARunThatOutlastsTheReadTimeoutCompletes` guards the 15 s read timeout against cutting a run short: Go clears a connection's read deadline once the body has been read. It passes already.

**Expected failures**

- `TestPostRunAnswers400ForDataAfterTheJSONValue`: the decoder stops at the end of the JSON value, so data after it is accepted (200).
- `TestAClientWhoseRequestsAreStillSendingBodiesGets429AtOnce`: requests count against the client only once their bodies are read, so the third gets 200.
- `TestBodiesBeyondTheReadLimitGet503AtOnceUntilOneFinishes`: nothing limits bodies being read, so the third gets 200.
- `TestAFinishedRunReleasesItsSlotBeforeItsResponseIsWritten`: the slot is held until the response is written, so the second run gets 429.
- `TestARequestWhoseBodyStallsGets408AndItsConnectionCloses`, `TestAConnectionIdleBetweenRequestsIsClosedAfterTheIdleTimeout`: the server sets neither timeout, so nothing happens within 3 s.
- `TestAClientThatDisconnectsAfterAPaddedBodyEndsItsRun`: the body is never read to its end, so the disconnect goes unnoticed.
- `TestAResponseTheClientDoesNotReadIsAbandonedAfterTheResponseTimeout`: the write blocks indefinitely, so the client's next run gets 429 for 3 s.
- The three config tests: `SANDBOX_READ_CONCURRENCY` is not read and has no default.
- `TestARequestWhoseBodyStallsGets408After15Seconds`: no response within 30 s.

**Evidence**

- Locally: `gofmt` and `go vet` (also with `-tags integration` and `-tags deploy`) pass. `go test -race ./...` fails exactly the eleven new unit tests above, for the reasons given; `TestARunThatOutlastsTheReadTimeoutCompletes` and every existing test pass.

**Anticipated implementation**

A prototype of this, not committed, passes every unit test three times under the race detector.

- `internal/api/limits.go`: `enter` counts a request against its client and reserves a body read before the body is read; `admit` keeps the rate limit and run slots. A client is recorded in the per-minute table only when a run starts.
- `internal/api/server.go`: `run` calls `enter`, decodes, frees the read, then `admit`s; it releases the slot as soon as the executor returns and sets a write deadline of `ResponseTimeout` before writing. `decode` reads to the end of the body, refusing anything but whitespace after the value, and answers 408 with `Connection: close` when the read times out. `HTTPServer` sets `ReadTimeout` and `IdleTimeout`.
- `internal/config`: `SANDBOX_READ_CONCURRENCY`, default 64.
- `cmd/runner-api`: 15 s read, 3 minute idle and 10 s response timeouts.
- README and plan: `SANDBOX_READ_CONCURRENCY`, and `SANDBOX_CLIENT_CONCURRENCY` counting requests from their arrival.
