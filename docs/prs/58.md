# Pin nsjail to a reviewed commit and report upstream changes

Closes #58. Part of #1.

## Summary

The image builds nsjail from a commit named by its full hash instead of the tag `3.6`, which could be moved to other content. A weekly workflow compares the pinned commit with nsjail's master and keeps one issue open while master has moved past it, saying how far, or that master no longer contains the pinned commit. Caddy stays on `caddy:2`, which the daily update keeps patched.

The commit pin comes from Neil Kirsopp's review (branch `harden-run-isolation` of cursork/sandbox).

## How it was tested

Unit tests run the check's script on each kind of comparison and read the Containerfile and the workflows: the nsjail commit is a full hash, and the one job that writes issues writes nothing else. The integration, UI and deployment suites run against the image built from the pinned commit.

**Decisions in the tests**

- The workflow fetches master's head and GitHub's comparison of the pin with master, and hands them to `scripts/nsjail-upstream`, which decides and writes the issue's body; the tests run the script as the `needs-build` tests run theirs. Its arguments are the pinned commit, master's head, the comparison's status and its count of commits master has past the pin, and the latest release's tag. It exits 0 with a report, 1 when the pin is master's head, and 2 on arguments it cannot read, so that a failed API call never closes the issue.
- GitHub's status `behind` or `diverged` means the pinned commit is not in master's history; the report says so, as a sign of a rewritten history, rather than counting commits.
- The pin test reads `ARG NSJAIL_COMMIT`, which the workflow also reads, and requires that the build uses it and clones no branch or tag.
- The permission test generalises the existing one for packages: exactly one job can write issues, and it can write nothing else.

**Expected failures**

- The four `TestTheNsjailCheck...` tests: `scripts/nsjail-upstream` does not exist.
- `TestTheImageBuildsNsjailFromACommitNamedByItsHash`: the Containerfile clones the tag `3.6`.
- `TestTheOneJobThatWritesIssuesWritesNothingElse`: no job can write issues.

**Evidence**

- Locally: `gofmt` and `go vet` pass, and `go test ./test/workflows/` fails exactly these six tests for the reasons above.
- CI run [45838732672](https://github.com/abrudz/sandbox/actions/runs/45838732672) on `88892fb`: the lint and unit job fails exactly these six tests, for these reasons. The image builds from the tag, and the integration, UI and deployment suites pass.

### Cycle 2: GREEN

**Changes**

- `image/Containerfile`, in Neil Kirsopp's commit: `ARG NSJAIL_COMMIT`, the commit the tag `3.6` named (`f784754`), checked out after a full clone.
- `image/Containerfile`, on top of it: the pin is `ec259a3`, master's head on 2026-11-20, 157 commits after 3.6. The build fetches only that commit, checks that it has it, and takes the submodules it names (Kafel `df38168`). The unused `NSJAIL_VERSION` is gone.
- `image/nsjail.patch`: rebased onto `ec259a3`, whose `cgroup2.cc` computes `mem_max` before writing `memory.max`. The changed lines are the same; upstream writes neither `memory.oom.group` nor a 100 ms `cpu.max` period, so both hunks are still needed.
- `scripts/nsjail-upstream` and `.github/workflows/nsjail.yml`: every Monday, and on demand, the workflow reads the pin, asks GitHub for master's head, the comparison and the latest release, and opens, updates or closes the issue "Review nsjail's changes past the pinned commit" through the REST API. A push that changes the workflow, the script or the Containerfile runs the comparison and writes no issue. The job can read the repository and write issues, nothing else.
- `THIRD_PARTY_NOTICES`, `image/nsjail.cfg`'s comments, README and the plan name the pinned commit rather than 3.6. README says Caddy stays on `caddy:2`, which the daily update keeps patched.

**Review of 3.6 to `ec259a3` against this configuration**

- Nothing in `image/nsjail.cfg` has to change. Every field it uses keeps its name, default and meaning; new fields (`oom_score_adj`, `seccomp_unotify`, `use_core_scheduling`, traffic rules, the `user_net` backends nstun and pasta) are off unless configured, and the legacy mount backend is still the default.
- Changes on paths this configuration uses, each stricter than before: bind mounts are made from a descriptor opened on the source, not its path; the read-only remount runs before `pivot_root` and reaches the submounts of recursive binds, so Docker's `/etc/hosts`, `/etc/hostname` and `/etc/resolv.conf` are read-only in the jail; failures of `setgroups`, `no_new_privs` and `setsid` stop the run instead of being logged; directories are created with `O_NOFOLLOW`; the parent-death signal is armed earlier.
- Kafel `76d0f41` to `df38168`: big-endian argument order, jumps over 255 instructions and comment parsing. No syntax change, and no change to the x86_64 tables, the architecture check or x32 handling.
- No binaries, no new submodules and no new network fetches in the build. The nstun and seccomp notification code (about 6,400 lines) was not read in detail: it is compiled in, but this configuration cannot reach it.
