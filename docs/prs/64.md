# Read a run's outcome only from nsjail's own log lines

Closes #64. Part of #1.

## Summary

runner-api tells how a run ended only from whole lines in nsjail's INFO format, `[I][<time>] pid=<n> ([STANDALONE MODE]) exited with status: <s>, (PIDs left: <k>)` and its `terminated with signal` and `run time >= time limit` counterparts, instead of from those words anywhere in the log. It keeps at most 64 KiB of nsjail's log and drains the rest. `image/nsjail.cfg` says that a log level below INFO writes the run's arguments into the log, where an argument holding a line break could forge an outcome line.

## How it was tested

Unit tests stand the test binary in for nsjail: it writes a given log to descriptor 3 and exits. They check that INFO lines decide the outcome, that the same words inside another line do not, and that a 4 MiB log reaches runner-api's report as at most 64 KiB. The integration suite runs the real nsjail, whose lines the patterns must match for any run to succeed.

**Decisions in the tests**

- `TestMain` makes the test binary a fake nsjail when `FAKE_NSJAIL_LOG` is set, before the testing package reads its flags, so `Run` starts it with nsjail's arguments, which it ignores. The log lines follow nsjail's `logs.cc` and `subproc.cc` at the pinned commit: `[I][%FT%T%z]`, then the message, with signal names such as `SIGKILL`.
- The forged lines are DEBUG lines that hold the phrases as an argument would, including a whole outcome message that is not at the start of its line. The real outcome is exit status 3, so a forged signal or time limit shows.
- The size test writes 4 MiB of DEBUG lines and no outcome line, so `Run` reports the log through `Logf`, and checks the size of what `Logf` receives.

**Expected failures**

- `TestAnOutcomePhraseInsideAnotherLogLineDoesNotDecideTheResult`: each forged phrase decides the result (SIGKILL, or a time-out).
- `TestRunKeepsAtMost64KiBOfNsjailsLog`: `Logf` receives the whole 4 MiB log.
- `TestRunReadsTheOutcomeFromNsjailsInfoLines` passes already.

**Evidence**

- Locally: `gofmt` and `go vet` pass, and `go test ./internal/sandbox/` fails exactly the two tests: a forged `terminated with signal: SIGKILL (9)` gives signal SIGKILL and a forged `run time >= time limit` a time-out, where the run exited with status 3; `Logf` receives 4,194,365 bytes.

### Cycle 2: GREEN

**Changes**

- `internal/sandbox/nsjail.go`: the three patterns match a whole line (`(?m)^…$`) in nsjail's INFO format; the log is read through the same `capped` writer as the run's output, with a 64 KiB limit.
- `image/nsjail.cfg`: the comment on `log_level` says INFO is the lowest safe level, and why.

**Evidence**

- Locally: `gofmt`, `go vet` and `go test ./internal/sandbox/` pass.

The three unit tests pass in the lint and unit job; every run in the integration and UI suites, ending by exit, signal or time limit, is read through the anchored patterns from the real nsjail's log; the deployment suite passes.
